=encoding UTF-8

=head1 NAME

D2TG::Reply::Args - CLI argv-parsing helpers shared by cli/reply.pl and other cli/*.pl scripts

=head1 SYNOPSIS

    my ( $bot_token, @rest ) = D2TG::Reply::Args::extract_bot_flag(@ARGV);
    my ( $bot_token, @rest ) = D2TG::Reply::Args::extract_bot_flag_or_die(@ARGV);
    my ( $chat_id, $text, $reply_to_message_id ) = D2TG::Reply::Args::parse_cli_args(@ARGV);
    my $value = D2TG::Reply::Args::_extract_leading_flag_value( \@args, '--some-flag' );

=head1 DESCRIPTION

TGT-265: extracted out of L<D2TG::Reply> (which owned these three
functions since TGT-057/TGT-042/TGT-236) into their own module - CLI
argv-parsing is a distinct concern from L<D2TG::Reply>'s own
send/voice/store-write concern, and L<extract_bot_flag_or_die()|/extract_bot_flag_or_die(@args)> is
already called by 9 C<cli/*.pl> scripts beyond C<reply.pl> (TGT-311
added C<fetch.pl> as the 9th), so it isn't really reply-specific logic
either. Mirrors
L<D2TG::Store::RetryQueue>/L<D2TG::Config::Paths>'s own precedent.

=head1 FUNCTIONS

=head2 _extract_leading_flag_value($args, $flag)

TGT-322 (found via a live JOB-003 hourly bug hunt, extracted in the
same ticket that introduced its second call site - the same "found it
twice, extract it" convention this project has followed since
TGT-167/170/171/172/177/181/279/310/313/314/317/318/320): both
L<extract_bot_flag()|/extract_bot_flag(@args)> and
L<parse_cli_args()|/parse_cli_args(@ARGV)> independently implemented
the identical shape - if the flag is the very first element of the
array, shift it off and shift-and-validate the following value via
L<D2TG::Config::Flags/shift_flag_value>; otherwise return C<undef> and
leave the array untouched. Takes C<$args> by array reference (mutating
it in place on a match, matching L<D2TG::Config::Flags/shift_flag_value>'s
own by-reference convention) and the flag's own literal string. Pure
extraction - both callers are byte-identical in behavior to their
pre-extraction selves.

=head2 extract_bot_flag(@args)

Parses a leading C<--bot <token>> pair off the front of C<@args> (TGT-057),
returning C<($bot_token, @remaining_args)> - via
L<_extract_leading_flag_value()|/_extract_leading_flag_value($args, $flag)> (TGT-322).
C<$bot_token> is C<undef> when
C<--bot> isn't the first argument - C<cli/reply.pl> falls back to C<D2TG::Config::token>
(C<D2TG_TOKEN>) in that case, unchanged from before this ticket. Leading,
not whole-list, for the same collision-avoidance reason as
C<D2TG::Config::Flags::extract_db_flag> and C<--reply-to-message-id>'s
own leading-only recognition (TGT-042, moved from trailing-only by
TGT-322): free reply text passed as multiple
unquoted shell words could otherwise contain the literal token C<--bot>
and be misread as the flag.

When C<--bot> is the first argument, its value is validated via
L<D2TG::Config::Flags/shift_flag_value> (TGT-074, same bug class as TGT-071's
C<--db> fix): dies with C<--bot requires a value> if it's missing,
empty, or itself flag-like, instead of silently returning another
flag's own name as the bot token (e.g.
C<extract_bot_flag('--bot','--db','myalias',...)> previously returned
C<'--db'> as the token). This includes a sole bare C<--bot> with I<no>
other argument at all (TGT-264, found via a scheduled JOB-003 hourly
bug hunt) - the guard used to require at least 2 args before even
checking, so C<extract_bot_flag('--bot')> silently fell through to
returning C<(undef, '--bot')> instead of dying like every other
malformed shape above; now C<--bot> alone is the same
C<--bot requires a value> die as any other empty-value case, since
L<D2TG::Config::Flags/shift_flag_value>'s own underlying call already dies correctly when
shifted off an empty list.

=head2 extract_bot_flag_or_die(@args)

TGT-236: centralizes the idiom that 10
C<cli/*.pl> scripts (C<history>, C<attachment>, C<unread>,
C<retry-download>, C<retry-transcription>, C<approve>, C<send>,
C<reply>, C<fetch>, C<whoami> - TGT-340 added the 10th) each duplicated around L<extract_bot_flag()|/extract_bot_flag(@args)> - the exact
duplication class that already
caused TGT-068/074/231. A one-line forwarder onto the shared
L<D2TG::OrDie/or_die> helper (TGT-269, found via a scheduled JOB-004
improvement hunt: this same eval/print-STDERR/exit(1) wrapper shape
was found duplicated a further 3 times across other modules) -
C<or_die> calls L<extract_bot_flag()|/extract_bot_flag(@args)> in an C<eval>; on failure, prints
the error to STDERR and calls C<exit(1)> instead of propagating a raw
exception. On success, returns exactly what C<extract_bot_flag>
returns (C<$bot_token> may still be C<undef>) - this helper does not
apply any default-to-C<''> or positional handling itself, since that
differs legitimately between callers: a leading-position single call
site (C<history.pl> and siblings) versus a caller embedded in a
multi-flag dispatch loop (C<send.pl>/C<reply.pl>, both of which now
call this function unconditionally whenever C<$ARGV[0] eq '--bot'>,
matching every other caller - TGT-268, found via a scheduled JOB-003
hourly bug hunt, removed a stale C<@ARGV E<gt>= 2> special-case both
scripts used to pre-check, which had silently reintroduced the exact
bare-C<--bot> bug TGT-264 already fixed inside L<extract_bot_flag()|/extract_bot_flag(@args)>
itself). L<extract_bot_flag()|/extract_bot_flag(@args)> itself is unchanged.

=head2 parse_cli_args(@ARGV)

Parses C<cli/reply.pl>'s raw argument list into C<($chat_id, $text,
$reply_to_message_id)> (TGT-042). C<--reply-to-message-id <id>> is
recognized I<only> in the leading position - immediately before
C<chat_id> - via L<_extract_leading_flag_value()|/_extract_leading_flag_value($args, $flag)>, matching
exactly how the poller's own C<REPLY WITH> template (TGT-040) now
prints it (TGT-322 moved both).

TGT-042 originally made this trailing-only (the last two elements of
the argument list) specifically to avoid a whole-list scan colliding
with free reply text. TGT-322 (found via a live JOB-003 hourly bug
hunt) found that trailing-only recognition still left a real gap: a
reply message that legitimately I<ends> with the literal words
C<--reply-to-message-id <word>> (e.g. a question about the flag
itself) was silently corrupted - those two trailing tokens were
stripped and misread as the flag, discarding the operator's real
message and fabricating a bogus C<reply_to_message_id> from unrelated
content. Reproduced live:
C<parse_cli_args('12345','how','do','I','use','--reply-to-message-id','5')>
returned C<$text = 'how do I use'> and
C<$reply_to_message_id = '5'> instead of preserving the full text.
Since TGT-042's trailing-only design was itself a deliberate, reasoned
choice (not an oversight), this was raised as a question (Q-019) rather
than reversed unilaterally - Michael's answer chose the structural fix:
recognize the flag only in the leading position instead, the same
principle L<extract_bot_flag()|/extract_bot_flag(@args)>'s own TGT-227
fix already established for C<--bot> - a leading flag never scans into
the free-text region at all, so it can never collide with reply text no
matter what that text contains. A bare leading C<--reply-to-message-id>
with no value, or immediately followed by another flag-like token, now
dies C<--reply-to-message-id requires a value> (matching
C<--bot>/C<--db>'s own existing convention) instead of the old
trailing-only code's silent fall-through into ordinary text.
C<$reply_to_message_id> is C<undef> when the flag isn't given (or isn't
leading). Does not validate that C<$chat_id> or C<$reply_to_message_id>
are numeric; C<cli/reply.pl> does that itself before using the parsed
result.

Decodes every argument as UTF-8 before doing anything else (TGT-073, a
real bug found by a scheduled hourly bug-hunt): C<@ARGV> is always raw
bytes - Perl never decodes it as UTF-8 on its own - so non-ASCII reply
text (accents, CJK, Cyrillic, emoji) previously reached
L<D2TG::Telegram>'s C<encode_json> call as un-decoded bytes, which
C<JSON::PP::encode_json> treats as Latin-1 codepoints and re-encodes as
UTF-8, double-encoding every multi-byte character into mojibake (e.g.
C<h\x{e9}llo> arrived on Telegram as C<hÃ©llo>). Decoding here, once,
before C<$chat_id>/C<$reply_to_message_id> are even split off, fixes it
at the single chokepoint every C<cli/reply.pl> invocation passes through -
C<$chat_id>/C<$reply_to_message_id> are always plain ASCII digits, so
decoding them as UTF-8 is a harmless no-op. Only C<cli/reply.pl> reaches
this function via raw C<@ARGV>; no other C<cli/*> command's own
argv (C<--since>/C<--until> ISO timestamps, chat/message ids) carries
free-form user text through a similar chokepoint, so this is the only
place that needed the fix. A caller that ever passed an
I<already-decoded> wide-character Perl string here (rather than raw
bytes, which is what real C<@ARGV> always is) could in principle see
C<decode> mis-handle it - not a concern for the actual C<cli/reply.pl>
invocation path today, since C<@ARGV> is never pre-decoded.

=cut
